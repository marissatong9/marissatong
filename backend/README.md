# Backend

The portfolio API, built with Spring Boot 4, Java 25, Maven and PostgreSQL (Neon).

## Prerequisites

- **Java 25.** Check with `java -version`.
- **Docker Desktop**, running. Tests use it to start a throwaway Postgres.

You don't need to install Maven. Use the wrapper (`./mvnw`) in this folder.

## Getting started

1. Create `src/main/resources/application-local.properties` with your Neon **dev** branch details. This file is gitignored, so never commit it.

   ```properties
   DB_URL=jdbc:postgresql://<dev-host>/<database>?sslmode=require
   DB_USER=<user>
   DB_PASSWORD=<password>
   ```

   In the Neon console, open **Connect**, pick the `dev` branch, and copy the connection string. Add the `jdbc:` prefix, move the user and password out of the URL, and keep `?sslmode=require`.

2. Run the app with the `local` profile:

   ```bash
   ./mvnw spring-boot:run -Dspring-boot.run.profiles=local
   ```

3. Check it's running: http://localhost:8080/actuator/health should return `{"status":"UP"}`.

Stop the app with `Ctrl + C`. The app doesn't reload on code changes, so restart it after editing Java files.

## Commands

| Command                                                  | What it does                                    |
| -------------------------------------------------------- | ----------------------------------------------- |
| `./mvnw spring-boot:run -Dspring-boot.run.profiles=local` | Run the API on port 8080 against Neon `dev`     |
| `./mvnw verify`                                          | Compile, run tests and package the app          |
| `./mvnw test`                                            | Run tests only                                  |
| `./mvnw spotless:apply`                                  | Format all Java files                           |
| `./mvnw spotless:check`                                  | Report unformatted files (used in CI)           |
| `./mvnw clean`                                           | Delete the `target/` build folder               |

## Before opening a PR

Run the same checks CI runs (Docker must be running):

```bash
./mvnw spotless:check && ./mvnw verify
```

If `spotless:check` fails, run `./mvnw spotless:apply` and commit the changes.

## Project structure

```
src/main/java/dev/marissatong/portfolio/
  PortfolioApplication.java     Entry point, starts the app
  config/                       App configuration (CORS)
  controller/                   HTTP endpoints (URLs, request/response)
  service/                      Business logic
  repository/                   Database access (Spring Data JPA)
  model/                        Database entities (@Entity)
  dto/                          Request/response objects for the API
src/main/resources/
  application.properties        Shared settings (committed, no secrets)
  application-local.properties  Your local Neon dev details (gitignored)
src/test/java/dev/marissatong/portfolio/
  TestcontainersConfiguration.java  Throwaway Postgres for tests
```

## Architecture

Requests flow through three layers, each with one job:

```
┌──────────────────────┐
│  React Frontend App  │
└──────────────────────┘
          ▲
          │ HTTP request / response (JSON)
          ▼
┌──────────────────────┐
│   Controller Layer   │  ◄── HTTP routes, request parsing, input validation (@Valid),
└──────────────────────┘      status codes. No business logic.
          ▲
          │ DTOs (request / response objects)
          ▼
┌──────────────────────┐
│    Service Layer     │  ◄── Business logic and rules, transactions (@Transactional),
└──────────────────────┘      mapping between DTOs and entities. Knows nothing about HTTP.
          ▲
          │ Entities (@Entity objects)
          ▼
┌──────────────────────┐
│   Repository Layer   │  ◄── Database access via Spring Data JPA interfaces.
└──────────────────────┘      No logic.
          ▲
          │ SQL (generated by Hibernate, sent over JDBC)
          ▼
┌──────────────────────┐
│ PostgreSQL Database  │  ◄── Neon (dev / main branches), or Testcontainers in tests
└──────────────────────┘
```

| Layer      | Folder        | Example             |
| ---------- | ------------- | ------------------- |
| Controller | `controller/` | `ProjectController` |
| Service    | `service/`    | `ProjectService`    |
| Repository | `repository/` | `ProjectRepository` |
| Entities   | `model/`      | `Project`           |
| DTOs       | `dto/`        | `ContactRequest`    |

Each layer only talks to the one directly below it. Controllers never call repositories directly.

## Configuration

| Variable      | Local (`application-local.properties`) | Production (host environment variables) |
| ------------- | -------------------------------------- | --------------------------------------- |
| `DB_URL`      | Neon `dev` branch                      | Neon `main` branch                      |
| `DB_USER`     | Neon `dev` user                        | Neon `main` user                        |
| `DB_PASSWORD` | Neon `dev` password                    | Neon `main` password                    |

`application.properties` reads these as `${DB_URL}` and so on, so real values never go into git.

CORS allows browser requests to `/api/**` from `https://marissatong.dev`, `https://marissatong9.github.io` and `http://localhost:5173`. See `config/CorsConfig.java`.

## Tests

Tests use [Testcontainers](https://testcontainers.com/). Each run starts its own `postgres:17` container in Docker, runs the tests against it, and deletes it afterwards. Tests never touch Neon and don't need any environment variables.

If tests fail with `Could not find a valid Docker environment`, start Docker Desktop.

## CI

Pull requests into `main` that change `backend/**` run `.github/workflows/backend.ci.yml`:

- **Backend format:** `./mvnw spotless:check`
- **Backend build and test:** `./mvnw verify`

## Deployment

The API runs on an EC2 instance (us-west-2) at https://api.marissatong.dev. Merging a change to `backend/**` into `main` deploys it automatically with `.github/workflows/backend.deploy.yml`:

1. Checks formatting, runs the tests and builds the jar.
2. Gets short-lived AWS credentials through OIDC (no AWS keys are stored in GitHub).
3. Uploads the jar to S3 as `portfolio-api-<commit sha>.jar`.
4. Uses AWS Systems Manager (SSM) to run a script on the instance that downloads the jar, keeps the old one as `app.jar.prev`, and restarts the `portfolio` systemd service.
5. Waits for `/actuator/health` to report `UP`. If it doesn't, the script restores the previous jar and the run fails.

You can also run it by hand from the **Actions** tab (**Backend Deploy → Run workflow**).

| AWS resource                                | Purpose                                                           |
| ------------------------------------------- | ----------------------------------------------------------------- |
| S3 bucket `marissatong-portfolio-deploys`   | Stores the built jars                                             |
| IAM role `portfolio-ec2-role`               | Attached to the instance: SSM access and reading jars from S3     |
| IAM role `github-actions-portfolio-deploy`  | Assumed by GitHub Actions on `main`: uploads jars and sends SSM commands |
| GitHub repo variables                       | `AWS_DEPLOY_ROLE_ARN`, `DEPLOY_BUCKET`, `EC2_INSTANCE_ID`         |

On the instance, the app is `/home/ec2-user/app.jar`, its environment variables are in `/etc/portfolio/app.env`, and Caddy serves HTTPS in front of it. Useful commands:

```bash
sudo systemctl status portfolio   # is it running?
journalctl -u portfolio -f        # follow the logs
```
